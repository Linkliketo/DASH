# P1-1 可行性评估：PEAR vs 现有三段式管线 —— 决策报告

> **任务来源**：PROMPT.md §八 任务清单第 1 项
> **评估日期**：2026-07-24（P1 阶段）
> **决策问题**：是否用 PEAR（SIGGRAPH 2026，单模型前向回归）替换 DASH 的 MediaPipe Holistic → Kalman3D → SMPL-X L-BFGS 拟合三段式管线？
> **评估依据**：PEAR_analysis.md、comparison.md、MocapNET_analysis.md、PROMPT.md §5 已知风险

---

## 一、结论先行（TL;DR）

**不建议在 P1–P2 直接替换；建议"三段式为主干基线 + PEAR 作为 P3 决策门候选 + MocapNET 作为兜底 baseline"的三轨策略。**

理由一句话概括：

1. **PEAR 代码尚未开源**（项目页标注 coming soon），现在替换 = 项目进度押注在他人发布节奏上，不可接受；
2. **三段式的 SMPL-X L-BFGS 拟合环节本身存疑**（PROMPT.md §5.1 风险 #1：10,475 顶点逐帧迭代优化在 CPU 上做不到 ~15ms），但它暴露的是"拟合模块要降级"的问题，不是"整条管线要换"的问题——可用 MediaPipe 直接回归/轻量 NN lifting 先行兜底；
3. **PEAR 需要 GPU（ViT-B）**，与 DASH"消费级硬件、CPU 可跑"的核心卖点和 S3 推理优化子系统的工作定位存在张力；
4. 但 **PEAR 的精度和速度优势是真实的**（3DPW MPJPE 71.3、面部 LVE 1.22、GPU 上 28–43 FPS），必须纳入 P4 对比实验，否则论文审稿人一定会问。

---

## 二、三方案定义

| | 方案 A：三段式基线（现状） | 方案 B：PEAR 单模型替换 | 方案 C：折中（MocapNET 式） |
|---|---|---|---|
| 管线 | MediaPipe Holistic → Kalman3D → SMPL-X L-BFGS 拟合 → BVH | ViT-B 单模型 → EHM-s（SMPL-X+FLAME 参数）→ 映射 → BVH | MediaPipe 2D → NSRM + 朝向分类 SNN → BVH |
| 面部 | LibreFace 独立模块 → AU → RBF → 52 BlendShape | FLAME 50D 表情参数（内含），需 MLP 映射到 52 BlendShape | 仅 landmarks，无表情参数 |
| 状态 | 全部为已发布可复现组件 | 论文已发，**代码未开源** | 已开源（GPL），v4.0 2025.06 更新 |

## 三、决策建议表（核心交付物）

### 3.1 性能维度

| 指标 | 方案 A 三段式 | 方案 B PEAR | 方案 C MocapNET |
|---|---|---|---|
| 官方/预估延迟 | ~34ms（29 FPS），但 **L-BFGS 15ms 数字存疑，CPU 实测大概率秒级 → 需实测** | 推理 9–15ms + 动画 13–20ms ≈ 23–35ms（GPU 28–43 FPS） | 30Hz @ 笔记本 CPU（已验证） |
| CPU 可运行性 | MediaPipe/Kalman 可；**SMPL-X 拟合不可（风险 #1）** | ❌ ViT-B 在 CPU 上不可行 | ✅ 设计目标即 CPU 实时 |
| GPU 需求 | 无硬性需求 | RTX 3060 级起步（3090 实测 28 FPS） | 无 |
| 与 <100ms e2e 目标 | 若拟合换轻量方案可达标 | GPU 上达标，CPU 不达标 | 达标 |
| 抖动控制 | Kalman3D ±2.3→±0.4cm（设计值，待实测） | 单帧回归无时序滤波，**需额外加滤波/时序模块** | 无滤波，抖动大 |

### 3.2 精度维度

| 指标 | 方案 A 三段式 | 方案 B PEAR | 方案 C MocapNET |
|---|---|---|---|
| 身体（3DPW MPJPE↓） | 未实测（拟合精度受 2D 关键点误差传播限制） | **71.3（SOTA 级）** | 无公开可比数字，SNN 精度弱于深度方法 |
| 面部（LVE↓） | 依赖 LibreFace AU 间接评估，几何精度未知 | **1.22（碾压级，专用面部方法 SMIRK 为 8.02）** | 无面部几何输出 |
| 手部（PA-PVE↓） | MediaPipe 手部 21×2 直接可用 | 12.8（优于 OSX/Multi-HMR） | 有但精度一般 |
| 微表情语义（AU） | ✅ 17 AU 强度，语义可解释、可映射 BlendShape | ❌ FLAME 系数无语义，AU 需另算 | ❌ |

### 3.3 工程量维度

| 维度 | 方案 A 三段式 | 方案 B PEAR | 方案 C MocapNET |
|---|---|---|---|
| 可获得性 | ✅ 全部 pip/官网可得 | ❌ **coming soon，时间不可控** | ✅ GitHub 可 clone |
| 集成工作量 | 中（三模块 + 同步机制，S3 异步管线工作量大） | 小-中（单模型，省掉同步），但需新增 FLAME→BlendShape 映射 + BVH 导出 | 小（直接用） |
| 训练需求 | 几乎无（全冻结 + 经典算法） | 不训练仅推理则无需；微调需 8×A6000 级算力 → **超 DASH 预算** | 无 |
| 依赖风险 | MediaPipe 闭源但稳定；SMPL-X 需申请 license | 开源时间、license、依赖 GUAVA 渲染器均未知 | GPL license 与 DASH 开源计划冲突需注意 |
| 对 S3（推理优化）的接口 | 清晰：LibreFace/拟合网络均可 QAT+ONNX | ViT-B 量化比 ResNet-18 难，但 INT8 ViT 已有成熟实践 | SNN 太小，无量化优化空间 → **S3 无事可做** |

### 3.4 与创新点的关系（最关键的一维）

DASH 的三个创新点：① 统一全身+微表情高速框架；② 摄像头→引擎端到端管线；③ 消费级硬件联合推理部署（压缩 85%）。

| 创新点 | 方案 A | 方案 B PEAR | 方案 C |
|---|---|---|---|
| ① 统一框架 | ✅ asyncio 多模态同步本身是贡献点 | ⚠️ 身体面部统一是 PEAR 的贡献，DASH 退化为"PEAR + 映射 + 部署"，创新叙事被削弱 | ✅ 但面部需自行补齐 |
| ② 端到端管线 | ✅ 完全自有 | ✅ 保留（映射+BVH+引擎桥接仍是自有工作） | ✅ |
| ③ 消费级部署 | ✅ CPU 友好是核心卖点 | ❌ 与 GPU 依赖直接冲突；若改走"数据生成与渲染分离"（PROMPT 风险 #3）可部分缓解 | ✅ 但没有可压缩的大模型，85% 压缩指标无法达成 |
| 论文故事完整性 | "轻量管线 + 系统优化" | "SOTA 模型 + 工程化落地"（偏工程，学术贡献变弱） | "复现 + 增量"，最弱 |

**结论：方案 B 若不加改造地采用，会掏空创新点 ①③；方案 A 是对创新叙事最有利的主干，但必须解决拟合模块的 CPU 可行性问题。**

### 3.5 综合评分（1–5，5 最优；权重按 DASH 项目目标设定）

| 维度（权重） | 方案 A | 方案 B | 方案 C |
|---|---|---|---|
| 性能/实时性（25%） | 3（拟合模块待救） | 5（仅 GPU） | 4 |
| 精度（20%） | 3 | 5 | 2 |
| 工程量/进度可控（25%） | 4 | 2（未开源） | 5 |
| 创新性保持（30%） | 5 | 2 | 2 |
| **加权总分** | **3.75** | **3.30** | **3.15** |

## 四、风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| PEAR 不开源/延迟开源 | 中 | B 方案整体不可用 | 主干不依赖 PEAR；P3 决策门再评估 |
| 方案 A 的 L-BFGS 拟合 CPU 不达标（风险 #1） | **高** | e2e <100ms 目标失守 | **立即行动**：P1 内实测；不达标则降级为低迭代数 / MediaPipe 3D 直接驱动 / 轻量 2D→3D lifting NN（G2O-Pose、数千参数 landmark NN） |
| PEAR 在 DASH 自采场景精度下降 | 中 | 对比实验失真 | 用 500 样本验证集双方同测，协议一致（§六 Benchmarking 铁律） |
| FLAME 50D → ARKit 52D 映射损失 | 低-中 | 面部表现力下降 | MLP 映射已有 Gaussian Head Avatars 验证可行；合成配对数据流程即任务 P2-1 |
| MocapNET GPL 污染 | 低 | 开源合规 | 仅作 baseline 对比，不拷贝代码进 DASH 仓库 |

## 六、给负责人的备注

- 本决策**不影响** S2（LibreFace 面部模块）的独立开发——即使未来切到 PEAR，AU→BlendShape 的语义映射链路仍是 DASH 差异化卖点（PEAR 给的是几何不是语义）。
- 方案 A 的最大短板（拟合模块）与 PEAR 是否采用**无关**，它本来就必须修。建议把"拟合模块降级方案"列为 P1-2 任务的子项。
- 所有性能数字凡标注"需实测"处，在 benchmark 文档（任务 P1-4）中落实具体测量协议。
