### 1.2 本阶段的首要目标（重要）

**首要目标是能力提升，而非交付成果。** 项目最终展示需要产品，但选路的判据是「哪条路径对负责人能力的提升最大」。

据此对候选路径的评估：

| 路径 | 是否跨过单文件脚本复杂度 | 反馈速度 | 能力缺口匹配 | 结论 |
|---|---|---|---|---|
| 量化实验 | 部分（工具链为主） | 慢 | 中 | 选为**风险前置项** |
| 感知管线 | 是（多模块） | 快 | 高 | 选为**主战场** |
| 身体动捕 → BVH | 是 | 中 | 高 | 选为**可选项** |

**能力缺口的诊断依据**：上一阶段暴露的错误集中在同一类——多步运行程序中的**状态、作用域、时序**管理（变量被意外重定义、缩进层级错误、状态更新时序颠倒、循环内状态未推进、绝对量与相对量混淆）。这类能力无法通过阅读获得，只能在编写复杂度超过单文件脚本的程序时长出来。

### 1.3 次要目标（并行成立，不冲突）

本项目同时是 Mitacs GRI 2027 面试的核心材料，面试官最可能追问本项目的技术细节。本阶段选定的两条路径恰好对应面试暴露度最高的两个缺口：

| 面试缺口 | 暴露度 | 本阶段对应内容 |
|---|---|---|
| INT8 量化原理 | 很高 | 阶段 0–1、阶段 4 |
| 结构化剪枝 | 很高 | 阶段 4 |
| ONNX Runtime 优化 | 高 | 阶段 0–1、阶段 4 |

## 四、决策门（阶段 0 的出口）

阶段 0 只回答三个问题，然后按结果分支。

| # | 探针问题 | 为「是」 | 为「否」 |
|---|---|---|---|
| Q1 | 能否从 `.task`（ZIP 包）中拆出独立的 `.tflite` 文件？ | 继续 Q2 | 改对象：改用 LibreFace 的 PyTorch 权重，或自建小网络 |
| Q2 | 能否跑通 PTQ（训练后量化）得到 INT8 模型？ | 继续 Q3 | 换工具链：改走 ONNX 量化，或用 NumPy 手写量化模拟 |
| Q3 | 能否测出**延迟 / 体积 / 精度**三个数？ | **进入阶段 1** | 先解决测量方案 |

### 4.1 时间盒（timebox）

**阶段 0 的硬性上限为 2 天。** 到期未有结论即停止深入，按上表选择一条分支继续，不得在工具链中继续消耗时间。这是防止阶段 0 拖垮全局的保险机制。

### 4.2 量化对象的两个候选

| 候选 | 优点 | 缺点 |
|---|---|---|
| A. MediaPipe 的 `.task` 模型 | 是真实目标，面试叙事最贴切 | 需 TFLite → ONNX 转换，风险较高 |
| B. 自行训练的小映射网络（PyTorch，如 landmarks → blendshapes 的 MLP） | 工具链 100% 在手；模型确实自有，QAT 与剪枝在原理上才真正成立 | 不是原始 `.task` 模型 |

**处理方式**：探针中两条都试。二者共享后半段流程（ONNX 量化 + 测量），因此哪条走通都不浪费；两条都通则对比材料更丰富。

**候选 B 的训练数据来源（无需额外采集）**：用现成的 MediaPipe 管线在已有图片/视频上跑一遍，即可自动获得「478 关键点 → 52 表情系数」的成对样本（相当于对原模型做知识蒸馏），训练数据可自产。

**候选 B 与阶段 4 剪枝的关系（重要）**：结构化剪枝需要一个可访问权重图的模型。MediaPipe 的 `.task` 是锁定包，无法剪枝。因此——**若量化对象选定候选 A，阶段 4 的剪枝实验仍在候选 B（自训练网络）上完成**，使「量化 + 剪枝 + ONNX 部署」三项技术都能真实演示。这也让候选 B 无论探针结果如何都有用途。

### 4.3 分支的共同保证

**无论走哪条分支，都必须产出「实测数字」。** 面试的风险不在「使用了什么工具」，而在「是否只会背概念」。

## 五、模块结构与接口（阶段 2 目标形态）

### 5.1 目录结构

```
deploy/
├── 01_single_image.py        保留
├── 02_realtime.py            保留（作为重构前的参照基线）
└── dash/                     新增：包
    ├── __init__.py
    ├── types.py              数据契约
    ├── capture.py            采集：摄像头 → 帧 + 时间戳
    ├── perception.py         感知：帧 → 关键点 + 表情系数
    ├── calibrate.py          校准：减去中性基线
    ├── smooth.py             平滑：滑窗 / Kalman
    ├── flow.py               光流（阶段 3）
    └── app.py                主循环：组装
```

### 5.2 数据契约

模块之间**不传递 MediaPipe 的原始对象**，只传递自定义的普通数据结构：

```python
@dataclass
class FaceObservation:
    timestamp_ms: int          # 真实时钟，单调递增
    landmarks: np.ndarray      # (478, 3) 归一化坐标
    blendshapes: np.ndarray    # (52,)   原始分数
```

**设计意义**：模块间只依赖此结构，则每个模块都能脱离其他模块单独测试——`perception` 可用单张图片测，`calibrate` 可用假数据测，`smooth` 可用随机数列测。

### 5.3 主循环形态

```python
while True:
    frame, ts = camera.read()               # capture 持有：时钟零点、帧号
    if frame is None:
        break

    obs = perception.process(frame, ts)     # perception 持有：模型句柄、上帧时间戳
    if obs is None:
        continue                            # 未检测到人脸

    obs = calibrator.apply(obs)             # calibrate 持有：基线向量 (52,)
    obs.blendshapes = smoother.update(obs.blendshapes)   # smooth 持有：滤波器历史

    render(frame, obs)
```

### 5.4 状态归属表

| 模块 | 持有的状态 | 生命周期 | 上一阶段对应的问题 |
|---|---|---|---|
| `capture` | 时钟零点、帧号 | 进程级，**永不重置** | `time_counter` 在循环中未推进 |
| `perception` | 模型句柄、上一帧时间戳 | 进程级 | 时间戳单调性 |
| `calibrate` | 基线向量 `(52,)` | 校准后固定 | — |
| `smooth` | 滤波器历史（上一帧值 / 协方差） | **逐帧更新** | — |
| `app` | 循环控制、采样计数 | 进程级 | 缩进层级、变量遮蔽 |

### 5.5 边界设计的验收标准

对任一模块，必须能立即回答三个问题：**它输入什么、输出什么、持有什么状态**。答不出来即表示边界未划清。

### 6.1 阶段 2 的等价性检查（重要）

重构最常见的失败模式是「改坏了但未察觉」。标准做法：**令 `02_realtime.py` 与 `dash/app.py` 处理同一段视频，对比输出的关键点与表情数值是否一致。** 这既是工程上「重构不改变行为」的常规验证，也是面试中可讲述的工程实践点。
