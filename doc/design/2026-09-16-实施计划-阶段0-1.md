## Task 2: 度量工具（先造尺子）

**Files:**
- Create: `D:\DASH\V0FastTest\quant\bench.py`

**Interfaces:**
- Consumes: 无
- Produces（后续 Task 4/6/8/9 都依赖这两个签名，**名字必须一致**）：

```python
def measure_latency(run_once, n_warmup: int = 10, n_runs: int = 100) -> dict:
    """run_once 是无参可调用对象，调用一次执行一次推理。
    返回 {'mean_ms': float, 'p50_ms': float, 'p95_ms': float, 'min_ms': float}"""

def file_size_bytes(path) -> int:
    """返回文件字节数。"""
```

**为什么先做这个**：没有尺子就无法比较 FP32 与 INT8。而且这把尺子**可以用已知答案校准**——见 Step 4。

- [ ] **Step 1: 写函数骨架**

需要用到（自己查文档确认参数）：`time.perf_counter`、`statistics.mean`、`statistics.median`、`numpy.percentile`。

`n_warmup` 的作用：**前若干次推理会明显偏慢**（delegate 创建、内存分配、缓存预热）。先跑掉它们再计时——这正是你在 `02_realtime.py` 里观察到的「第一个采样点永远偏低」的同一个现象。

- [ ] **Step 2: 冒烟测试**

调用 `measure_latency(lambda: None, n_runs=10)`。

**预期**：不报错，返回接近 0 的耗时。若报错，先修骨架。

- [ ] **Step 3: 用已知答案校准尺子（本任务的关键验收）**

写一段临时代码：用 mediapipe 加载 `D:\DASH\V0FastTest\models\face_landmarker.task`，构造一次推理并把推理调用包成 `run_once`，然后 `measure_latency(run_once, n_runs=100)`。

忽略 mediapipe 关于 xnnpack 与 feedback manager 的 WARNING（那是正常的）。

- [ ] **Step 4: 核对结果**

**预期**：`mean_ms` 落在 **11 – 14 ms** 区间。

**为什么这是验收标准**：你在 `02_realtime.py` 中已用完全不同的方式测得 11.7 – 13.2 ms（累计平均）。两把独立的尺子给出同一个答案 → 说明度量工具是对的。

| 结果 | 含义 |
|---|---|
| 落在 11–14 ms | 尺子可信，继续 |
| 明显更高（如 40 ms） | 多半漏了 warmup，或把图像预处理算进了计时 |
| 明显更低（如 2 ms） | 多半没真正执行推理（惰性求值），检查 `run_once` 是否被真实调用 |

- [ ] **Step 5: 记录并提交**

把你测到的数字写进 `quant/results/bench_baseline.md`（含日期、n_runs、四个分位数），然后：

- [ ] **Step 1: 选择量化方式并说明理由**

| 方式 | 特点 | 何时选 |
|---|---|---|
| 动态量化（dynamic） | 无需校准数据，权重量化、激活运行时量化 | 先试这个，最简单 |
| 静态量化（static） | 需要**校准数据集**，激活也量化，通常更快 | 动态量化精度不合格时 |

需要用到：`onnxruntime.quantization` 下的量化入口函数。

- [ ] **Step 2: 执行量化**

- [ ] **Step 3: 核对量化是否真的生效（关键）**

不要只看文件大小。检查两件事：
1. 模型里是否出现了 INT8 张量类型（可用 `onnx` 包遍历 `graph.initializer` 查看 `data_type`）
2. 加载后推理是否正常返回 52 维输出

**若体积没变小**：说明量化算子没被应用（常因算子版本不受支持），需要看量化时的日志输出。
